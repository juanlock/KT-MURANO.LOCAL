Development Standards

Applies every time a module is created or modified (Wake-up reloads it at the start of each session).

File uploads (user's rule, 2026-10-04)

  • Every file a module stores -- uploads, imported email attachments, generated documents -- goes to public/files/company_{id}/{module}/ (e.g. files/company_2/helpdesk/2026/10/…, files/company_2/email-office/…, files/company_1/products/…). One folder per company, one sub-folder per module. Never storage/app, never a shared folder for the whole install.
  • Use App\Support\CompanyFiles: dir($companyId, $module), putUpload(...) / putBytes(...) (adds {Y}/{m}/{random}-{name}), owns($path, $companyId, $module) before serving, download($path, $name). Store the path relative to public/ in the DB (files/company_…).
  • Private modules (bills, attachments, contracts, anything nobody should open by URL) pass $private = true: the module folder gets a .htaccess that blocks direct web access, and files are served only through an authorized controller (permission + same company + owns()).
  • Only a SuperAdmin, for install-wide/global settings (system logo, defaults), may write elsewhere under public/ (e.g. public/images/). Company Admins never write outside their own files/company_{id}/.
  • Company folders are git-tracked like the rest of public/files (they travel between machines with Pa Llevar) -- keep big imports in mind.

People, logins and permissions (user's rules, 2026-10-05 / 2026-10-06)

  • Every employee has a login. An employee always has its users row (type employee, employees.user_id), created automatically -- never "No user is linked to this employee". The Employee model's created hook provisions it through App\Services\LinkedUserService::provision() for any path (form, import, script); the login is active only when the company has a default employee password (Defaults -> Users), else disabled until System access sets one. Never insert employees with DB::table('employees')->insert() (it skips the hook) -- use the model, or provision the login yourself. Customers, suppliers and sales agents likewise get their login from their own module (LinkedUserService).
  • A customer is identified by email + company (user's rule, 2026-10-01). Automatic matching (online booking, imports, linked users) = same email in the same company only, otherwise a new customer; never match by phone, never across companies, never attach to the Walk-in customer; ask before merging. Only exception (2026-10-05): Zelle deposit emails carry just the payer's name, so there the same exact name in the same company = same customer.
  • Online booking (/book, 2026-10-07): only the name is required (email and phone optional; an email given must be valid). No email to the customer when they book -- only the company's admins get "new online booking"; the customer gets "your appointment is confirmed" when staff confirm it (if they gave an email; never the Walk-in / default customer). No email = a new customer. Limits per IP (booking_public_requests): 5 bookings / 10 min; from the 4th in 24 h the email is required and the booking waits for the "I agree" link we email (then that IP is free for 24 h). "Exit" / "Close" go to the code's ?return= website, only if it's in Online Booking -> Websites & codes (settings.booking_websites), else the first one, else the company website.
  • Public links use App\Support\PublicUrl (2026-10-07), never the request's host / route(): the company's Public address (Defaults -> General, settings.public_base_url) else the server address APP_URL (System Settings -> General -> Server address, SuperAdmin; production = https://murano.kcoltech.com). Booking codes, and anything else pasted outside the app, are built with it.
  • Language follows the computer (user's rule, 2026-10-19): a device with no language chosen opens Murano -- login page, app, customer portal, PayPal pay page -- in the browser's language when it's an active one (English / Spanish; SetLocale::browserLocale(), i18n browserLocale()), else the company's default_language. A pick always wins: the user's own in the app (language_explicit), then this device's from the login page EN / ES switch (/set-locale -> cookie app_locale, also read by the SPA after sign-in). The standard login page texts have Spanish (migration 2026_10_19_130000); a company's own texts need their own Spanish in Settings -> Login Page.
  • Users -> Add creates Admin / SuperAdmin logins only (SuperAdmin only by a SuperAdmin). Employee / customer / supplier / sales-agent logins are created in HRM -> Employees, People -> Customers / Suppliers, Commissions -> Sales Agents (the server refuses them in Users -> Add). Users is where any login is edited (role, locations, password, PIN) and disabled (Active / Disabled switch -- never your own account).
  • The role is mandatory. A user can do only what their role allows (role_user -> permissions); no permission is granted by user type (SuperAdmin aside). Example: Email Office follows the role's email_office_view / email_office_manage checkboxes, Admins included. New features add their own permission checkbox (resources/src/config/permissions.js + a permissions row) instead of a type check.
  • Role home page (2026-10-06): roles.home_path (Roles -> "Home page") sends that role's users to a page instead of the dashboard (Home and the dashboard redirect there). Field roles use Daily Tasks (/service/daily, DailyTasksController): daily_tasks = own jobs (the service technician linked to my employee), start / complete with a note; daily_tasks_all = everyone's; daily_tasks_assign = assign the technician. Ruba: SupervisorRG (manager) and OperatorRG (field employees).
  • Payroll is weekly, by hours or commission (2026-10-06): employees.pay_type (hourly = hours on the service jobs they COMPLETE that week (work_hours, asked on Complete in Daily Tasks / the job's Task tab) x hourly_rate; commission = their sales that week (stylist on the sale's booking, else the sale's sales agent linked to their user) x commission_rate %), from pay_effective_from. HRM -> Payroll -> "Generate weekly payroll" (App\Services\PayrollRun); paid payrolls post to accounting via PayrollExpenseSync (Salaries and wages 7010 / Commissions 7040). Owners' own employee records (admin login) stay off payroll. Job cost = labor (hours x operator rate) + equipment used (service_job_assets, asset hourly_cost) -- App\Support\ServiceJobCost. Rates: Ruba manager $25 / operators $20, KcolTech $35, New Era 40% commission.
  • Global processes are transactional (user's rule, 2026-10-07): an action that changes several things does all of it in one DB transaction or none. Removing an employee = App\Services\EmployeeRemoval (employee out with leaving date, login disabled + signed out everywhere, technician / sales agent inactive, open service jobs / upcoming bookings / open tickets unassigned with a note, history kept, assets to collect reported). Disabling a login = App\Support\UserAccess::disable() (statut 0 + every token / session revoked); Is_Active refuses a disabled login before the request runs.
  • Sale numbers are per company (2026-10-07): SalesController::getNumberOrder($warehouseId, $companyId) = the company's own settings.sale_prefix + that company's highest number + 1, keeping its separator (Ruba INV_3604, KcolTech PP-…). Every place that creates a sale passes the location / company (sales, POS, bookings, contracts, online store).
  • Header icons (2026-10-07): System Settings -> Defaults -> Users -> Header icons (whole company) and Profile -> Header icons (each user: Company default / Show / Hide), App\Support\HeaderIcons + lib/headerIcons.js, the topbar uses auth.headerIcon(key). POS / Settings / Language keep their older switches (pos_settings.show_pos_button, customize_button_visible, show_language) as the company value. A new header icon gets a key in both lists. Each user can also change the icons' left-to-right order in Profile (2026-10-09; stored as _order in users.header_icons, HeaderIcons::userOrder(), topbar slots use auth.headerOrder(key) as the flex order -- a new icon goes in a tb-slot too).
  • Network security (user's rule, 2026-10-16): per company (Settings -> Network security, permission network_security, default off; on for KcolTech). Staff (admin / employee logins) can use the admin panel only from the company's networks (settings.network_allowed, IPs or CIDR ranges) or from an approved computer (key in the HttpOnly cookie murano_device, hash in trusted_devices; admins approve / remove). Checked at sign-in (LoginController) and on every staff request (Is_Active) via App\Support\NetworkAccess. Never applies to the SuperAdmin, customers, suppliers, the store, websites, portfolio, online booking or the portals. Users follow the company default unless users.network_access says restricted / anywhere. Production needs the server to pass the visitor's real IP (Hostinger proxy) before turning it on there.
  • PayPal module (user's rule, 2026-10-19): customers pay invoices into the company's OWN PayPal account. Business Module paypal, off by default (ModuleFlags::DEFAULT_OFF / modules.js defaultOff), on only for KcolTech; Ruba, New Era and Vanclem stay off until asked. Settings -> PayPal (paypal_manage, paypal_settings: Client ID / encrypted Secret, sandbox / live, webhook id, deposit account). The "Pay now" page is /pay/{sale} (relative signed link on PublicUrl, PayPalInvoicePayment::payLink; {pay_link} tag in invoice email / SMS / WhatsApp, "PayPal pay link" in the Sales row menu); a capture is recorded by PayPalInvoicePayment::record() (one transaction, once per capture: payment method PayPal, account balance, sale paid / status, paypal_payments). PayPalService::forCompany($id) = that company's keys; the online store's checkout still uses store_settings (not multicompany yet).
  • Employee details: View / Edit per tab (employee_tab_{tab}_{view|edit}, Roles -> HRM -> Employees; edit needs view), enforced server-side by App\Support\EmployeeTabs (also the company + own-record boundary for the endpoints behind the tabs). A new tab on that page gets its own pair of permissions.

User manual (user's rule, 2026-10-07)

  • In-app manual: the header book icon (manual header-icon key) opens components/ManualDrawer.vue -- This page (the entry / sections for the screen in use) or Whole manual (with search), in English or Spanish (follows the app language, switchable in the drawer). Content: resources/src/manual/manual.js, one entry per module with module (company switch, config/modules.js), perms (any) and screen paths; sections can narrow those again. A user only sees what their company has turned on and their role allows.
  • Every change to a module, form, screen, button, role or permission updates its manual entry in English AND Spanish in the same session (Pa Llevar step 00 checks it). A new module gets a new entry.
  • The overview by company and role (KT-TOOLS/Manual/murano_user_manual.html + .pdf, node KT-TOOLS/Manual/export_pdf.cjs) is refreshed when roles, home pages, company modules or guide steps change.

Online Store vs Website Management (user's rule, 2026-10-06)

  • Two separate modules, each with its own menus, options and files: Online Store (the shop: store_settings, files/company_{id}/store/) and Website Management (the company website: App\Models\WebsiteSetting, files/company_{id}/website/ -- own name, logo, favicon, SEO, top bar/footer, social links, menus). Imported websites live in files/company_{id}/website/sites/{name}/ (SiteImporter; moved out of store/sites/ on 2026-10-07 -- nothing of the website goes in store/). Their pages are edited in Website -> Pages (SitePageEditor): texts, pictures, links and, since 2026-10-07, Sections -- the blocks the menu jumps to (#x -> id="x" or class x) and blocks with an embed, edited as HTML (+ "Use our booking calendar" = /book?company={id}&embed=1). Company admins can't add scripts / event handlers there; only a SuperAdmin can. Same settings page (StoreSettings.vue), scope from route meta (/store/settings vs /website/settings).
  • Website pages (front page with our website theme, CMS pages, gallery, contact) render with WebsiteSetting::applyTo() and $website = true (no cart / search / shop category bar / shop sign-in); shop pages keep the store's settings. StoreFrontController::website().
  • Each website has its own address, never /online_store?company=ID: website_settings.url_path (Website settings -> Branding -> Website URL, e.g. /kcoltech, /kcoltech/pages/{slug}, /gallery, /contact; route groups per path in routes/web.php, WebsiteCompany middleware). Build website links with App\Support\WebsitePaths::url($rel, $companyId); old ?company= links 301 to the website address. New companies get a path from their name (WebsitePaths::suggest), system first segments are refused.
  • An import never loses the current website (2026-10-06): before Front page -> Import replaces the imported site, App\Services\WebsiteSnapshots::take() copies it to files/company_{id}/website/snapshots/{stamp}/ (table website_snapshots); Front page -> "Saved websites" lists them (Preview / Use this / Delete).
  • Theme-only tabs (user's rule, 2026-10-06): Hero, SEO, Top bar & footer and Social links show only when the front page uses our website theme; with an imported website they are hidden (it brings its own tags, header, footer and social icons). Website settings then shows Front page, Homepage blocks and Branding (Website URL, name, logo).
  • Gallery and Portfolio are their own modules: Gallery (/gallery, files/company_{id}/gallery/) and ONE Portfolio (the Portfolio module -- the old store_portfolio_* tables were merged into it; the website's Portfolio section reads portfolio_projects).
Frontend Conventions

(Reloaded by Wake-up, and shown in its report, like the Development Standards.)

  • Dropdowns are alphabetically sorted by default. Any <a-select>/combobox option list (Vue computed building {value, label} options) must be sorted alphabetically by its displayed label, using the shared sortByLabel() helper (resources/src/lib/filterOptions.js) -- wrap the options array in it rather than writing an ad-hoc .sort(). Apply this when creating a NEW dropdown, not just when fixing an existing one. Exceptions need a deliberate reason (e.g. a "Manage Menu" admin-defined order, or a list where recency/relevance genuinely matters more than alphabetical) -- default to alphabetical unless there's a reason not to.
  • Links to another module's page respect the role (2026-10-06): use <PermLink :to="..." permission="Sales_view"> (global component, components/PermLink.vue) instead of a bare <router-link> -- a user whose role can't open the target sees plain text, never a link to "no access". Use the target route's meta.permission.
  • Lists come back as they were left (user's rule, 2026-10-13). A list with filters registers them with useListState(key, { filters, datePreset, ... }, crud) (composables/useListState.js) during setup, before its first fetch: when the user returns with Back / Forward (the page's Back = $goBack, or the browser's) the filters, dates, page, page size, search and sort are restored; opening the list from the menu starts fresh. Forms opened from a list return with goBack(router, '/list') on Save and Cancel (never a bare router.push('/list'), which drops the filters). Done for Sales, Purchases, Quotations, Customers, Suppliers -- apply it to any list that gets filters.
