Run Protocol Copia BD:

1. Run `database/scripts/protocol_copia_bd.php` via tinker, using the file's **absolute path** (a bare relative `require` inside `php artisan tinker --execute="..."` fails with "Failed opening required" -- psysh's RequirePass doesn't resolve it against the project root). Example (adjust the drive/path to wherever this checkout actually lives on this machine):
   `php artisan tinker --execute="require '<absolute-path-to-repo>\database\scripts\protocol_copia_bd.php';"`
2. It reads the DB connection from Laravel's own config (never hardcoded) and shells out to `mysqldump` (`--routines --triggers --single-transaction`, streamed straight to disk rather than buffered in memory), writing the dump to **`KT-TOOLS/database/dbmurano_<date>_<host>_<time>.sql`** (e.g. `dbmurano_2026-09-29_KT-THUNDERA_11-23-38-AM.sql`) -- a new file each run, nothing overwritten, so backups accumulate as a history. `<host>` is the OS hostname (`gethostname()` -- no config needed, and it already matches this project's Kelsy location naming, e.g. `KT-THUNDERA` ~ "Thundera"); `<time>` is 12-hour with AM/PM so the filename itself reads as a time at a glance, not a bare digit run like `151648` -- hyphens throughout since `:` isn't valid in a Windows filename. Date/time come from Laravel's `now()`, which correctly reflects the real local clock now that `APP_TIMEZONE` is set to `America/New_York` app-wide (see CLAUDE.md -- it used to be `UTC`, several hours off the actual wall clock; this was fixed at the source, not worked around per-script).
3. `mysqldump`'s location varies per machine/engine, so the script discovers it in this order rather than hardcoding a path: `MYSQLDUMP_PATH` in `.env` (explicit override) -> `mysqldump` on PATH -> the `bin/` folder of whatever `mysql`/`mariadb` Windows service is currently running -> a couple of common XAMPP install locations as a last resort. If none of those find it, the script prints exactly what to add to `.env` on that machine and stops -- no partial/corrupt file is left behind.
4. **phpMyAdmin-ready (user's rule, 2026-10-01):** the file must import as-is through phpMyAdmin -> Import (e.g. Hostinger shared hosting) into whatever database is selected there. The script guarantees it:
   - **Order:** three passes in one file -- (1) every `CREATE TABLE` (+ routines), (2) every `INSERT`, (3) triggers last (so `kt_logs`' BEFORE INSERT trigger doesn't fire on the imported rows).
   - **No** `CREATE DATABASE` / `USE`, **no** `LOCK TABLES` (`--skip-add-locks`), **no** `DEFINER=` clauses, no MariaDB 11 sandbox first line.
   - Collations only MariaDB 11 (`utf8mb4_uca1400_*`) or MySQL 8 (`utf8mb4_0900_*`) know are rewritten to `utf8mb4_unicode_ci` -- on structure lines only; INSERT data is never altered.
   - `DROP TABLE IF EXISTS` before each table, so a re-import replaces the tables.
   Verified 2026-10-01 by importing a dump into a scratch local DB with the `mysql` client: 327 tables, 66,165 rows, zero count mismatches, trigger present.
4b. **Zipped (user's rule, 2026-10-05):** the database outgrew GitHub's 100 MB file limit (`office_emails` -- the Email Office import made the `.sql` ~123 MB), so the final backup is **`dbmurano_<date>_<host>_<time>.zip`**, holding the `.sql` of the same name (PHP `ZipArchive`, ~8x smaller). The plain `.sql` is deleted once the zip is written; if zipping fails the `.sql` is kept and a warning is printed. To restore: unzip, then import the `.sql` (phpMyAdmin also accepts the `.zip` directly when its upload limit allows the size). `*.zip` is stored with Git LFS (`.gitattributes`).
5. **Other folder:** to write the dump somewhere else under `KT-TOOLS/` (e.g. an export for an external backup program -> `KT-TOOLS/SQL/`), set `$outSubdir` before the require: `php artisan tinker --execute="$outSubdir = 'SQL'; require '<absolute-path-to-repo>\database\scripts\protocol_copia_bd.php';"`. Same format and file naming; default is `database`.
6. Report the output path and file size back to the user.

Why this exists: the user (jlock) hit a phpMyAdmin bug on this machine (`Export::exportDatabase()` `TypeError` on PHP 8.1+) where a failed export silently wrote phpMyAdmin's HTML error page into the `.sql` file instead of real SQL, which then failed to restore. This protocol is a reliable, phpMyAdmin-independent way to snapshot `dbmurano`, and since `KT-TOOLS/` is git-tracked (matching the existing manually-made dumps already in `KT-TOOLS/SQL/`), the snapshot travels with the repo across every machine this checkout is on -- same multi-machine intent as Kelsy/Preparate.

Note: `KT-TOOLS/database/` is **not** gitignored (same as the existing `KT-TOOLS/SQL/` dumps) -- each run adds a new file to be committed, so be mindful of repo size over many runs.
